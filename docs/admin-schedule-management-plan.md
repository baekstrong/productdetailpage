# 관리자 예약 일정 설정 기능 개발 계획

## 목적
원데이 수업 상세페이지의 `예약 가능 일정`을 하드코딩 목업이 아니라, 관리자가 직접 열고 닫을 수 있는 구조로 바꾼다.

## 사용자가 보는 화면
- 예약 가능 일정 달력
- 날짜별 표시 정보
  - 예약 가능 인원
  - 대기 인원
- 날짜 클릭 시 예약 신청 화면으로 이동
- 일반 달력 앱처럼 `<`, `오늘`, `>` 버튼으로 월 이동 가능
- 오늘 날짜는 달력 안에서 빨간 원형 표시

## 관리자가 설정해야 하는 항목
- 일정 생성
  - 수업 날짜
  - 시작 시간 / 종료 시간
  - 장소
  - 정원
  - 공개 여부
- 달력 공개/비공개
  - 공개: 사용자 달력에 노출
  - 비공개: 사용자 달력에서 숨김
- 예약 가능 인원
  - 정원 - 결제 확정 인원 기준으로 자동 계산
- 대기 인원
  - 해당 날짜 신청자 수 기준으로 자동 계산
- 상태값
  - 예약 가능
  - 대기 가능
  - 마감
  - 숨김

## 보안 전제
예약 시스템을 실제로 만들면 이름, 휴대폰 번호, 이메일, 신청 날짜, 결제 상태 등 개인정보가 서버에 저장된다. 따라서 관리자 기능은 단순 정적 페이지가 아니라 개인정보 저장/접근/삭제/로그 정책을 포함한 서버 기반 구조로 전환해야 한다.

### 개인정보 보안 조치
- HTTPS 적용
- 개인정보 DB 암호화 또는 최소한 민감 필드 암호화
  - 이름
  - 휴대폰 번호
  - 이메일
- 관리자 화면 인증 필수
- 관리자 비밀번호/토큰은 코드와 GitHub Pages에 저장하지 않음
- 서버 환경변수 또는 Secret Manager에 저장
- 예약 신청 데이터 접근 로그 기록
- 관리자 로그인 실패 로그 기록
- 개인정보 다운로드 기능은 기본 비활성화
- 필요 시 CSV 내보내기는 관리자 재인증 후 허용
- 개인정보 보관 기간 설정
  - 미결제/취소 신청: 수업 종료 후 30일 내 삭제
  - 결제 완료자: 정산/분쟁 대응 기간 후 삭제 또는 별도 보관 정책 적용
- 수신 거부/삭제 요청 대응 절차 마련
- Solapi API Key, 결제 API Key, 관리자 비밀번호는 절대 프론트엔드에 노출하지 않음

### 관리자 비밀번호 정책
- 관리자 모드 접속 시 비밀번호 입력 화면을 먼저 보여준다.
- 초기 비밀번호는 `8156`으로 설정한다.
- 단, `8156`은 HTML/JS에 직접 박아 넣지 않는다.
- 서버에서 입력값을 검증한다.
- 비밀번호는 서버에 평문 저장하지 않는다.
  - 서버 환경변수에는 해시값 또는 Secret으로 저장
  - 예: `ADMIN_PASSWORD_HASH`
- 로그인 성공 시 짧은 만료 시간의 관리자 세션 발급
  - 권장: 30분~2시간
- 로그인 실패 5회 이상이면 일정 시간 차단
- 관리자 URL은 공개될 수 있다는 전제로 설계한다.
  - URL 숨김이 아니라 비밀번호/세션/서버 검증으로 보호

### 서버/DB 후보 검토
1. Supabase
   - 장점: DB, Auth, Edge Functions, Row Level Security를 한 번에 구성 가능
   - 장점: 예약 데이터/관리자 인증/간단한 API 만들기 쉬움
   - 단점: RLS/정책 설정을 제대로 해야 함
   - 적합도: 가장 현실적인 1순위 후보

2. Firebase
   - 장점: Auth, Firestore, Hosting, Functions 생태계가 안정적
   - 장점: 관리자 로그인과 실시간 데이터 처리에 강함
   - 단점: 구조가 커지면 비용/규칙 관리가 복잡해질 수 있음
   - 적합도: 앱 확장까지 염두에 두면 후보

3. Vercel + Postgres/Supabase DB
   - 장점: Next.js 관리자 페이지, API Route, 서버 환경변수 관리가 쉬움
   - 장점: GitHub Pages보다 관리자 기능 구현에 적합
   - 단점: 현재 정적 GitHub Pages 구조에서 프레임워크 전환 필요
   - 적합도: 관리자/예약 시스템을 제대로 제품화할 때 후보

4. GitHub Pages 단독
   - 장점: 현재 구조 유지가 쉬움
   - 단점: 개인정보 저장, 비밀번호 보호, Secret 보호에 부적합
   - 결론: 공개 상세페이지 용도로만 유지. 실제 예약/관리자 시스템에는 부적합

### 서버 선택 1차 결론
- 공개 상세페이지: GitHub Pages 유지
- 예약 신청/관리자/문자 예약: Supabase 또는 Vercel API로 분리
- 추천 기본안: Supabase
  - `reservations` 테이블에 신청 데이터 저장
  - `classes` 테이블에 수업 일정 저장
  - 관리자 인증은 서버 검증 또는 Supabase Auth 사용
  - Solapi 발송은 Edge Function 또는 서버 API에서 실행

## 1차 구현
정적 GitHub Pages를 유지하면서 개인정보를 저장하지 않는 최소 관리 기능부터 만든다.

1. `data/classes.json` 생성
   - 공개 일정 데이터를 JSON으로 분리
   - index.html은 JSON을 읽어 달력을 렌더링
2. 관리자용 `admin.html` 추가
   - 일정 추가/수정/삭제 폼
   - 브라우저 localStorage에 임시 저장
   - JSON 내보내기 버튼 제공
   - 이 단계에서는 개인정보를 저장하지 않음
3. 관리자 모드 임시 보호
   - admin.html 진입 시 비밀번호 입력 UI 제공
   - 초기 비밀번호는 `8156`
   - 단, 이 방식은 정적 페이지 한계상 보안이 약함
   - 실제 개인정보 저장 전에는 반드시 2차 서버 인증으로 전환
4. 운영 방식
   - 관리자가 admin.html에서 일정 수정
   - JSON을 내려받아 `data/classes.json`에 반영
   - 커밋/푸시하면 공개 페이지 반영

## 2차 구현
수동 JSON 반영을 없애고, 서버 기반 일정 관리로 전환한다.

1. 서버 후보 결정
   - 1순위: Supabase
   - 대안: Vercel API + Postgres 또는 Firebase
2. `classes` 테이블 생성
   - 수업 날짜
   - 시작/종료 시간
   - 장소
   - 정원
   - 공개 여부
   - 상태값
3. 관리자 인증 적용
   - 관리자 모드 접속 시 비밀번호 입력
   - 입력 비밀번호 `8156`은 서버에서 검증
   - 비밀번호 원문은 프론트엔드/저장소에 노출하지 않음
   - 서버에는 해시 또는 Secret으로 저장
4. admin.html 저장 기능 연결
   - 일정 추가/수정/삭제 시 서버 API 호출
   - 공개 페이지는 서버 API 또는 공개 JSON API에서 일정 조회
5. 접근 제어
   - 관리자 API는 세션/토큰 없으면 차단
   - 공개 API는 공개 일정만 반환

## 3차 구현
예약/결제 흐름까지 연결한다. 이 단계부터 개인정보가 서버에 저장되므로 보안 조치를 필수 적용한다.

1. `reservations` 테이블 생성
   - 이름
   - 휴대폰 번호
   - 이메일
   - 원하는 날짜
   - 케틀벨 경험 여부
   - 수업을 듣고 싶은 이유
   - 신청 상태
   - 결제 상태
   - 생성일
2. 개인정보 저장 보안 적용
   - HTTPS
   - DB 접근 권한 제한
   - 민감 필드 암호화 또는 DB RLS 적용
   - 관리자만 신청자 상세 조회 가능
3. 예약 신청 폼 저장
4. 결제 안내 대상자 선별
5. 문자 발송 대상 리스트 생성
6. 결제 완료자 반영
7. 여석 발생 시 다음 대기자 안내
8. 개인정보 보관/삭제 정책 적용

## 4차 구현 — Solapi 문자 자동 예약
예약/결제/수업 전후 안내 문자를 Solapi로 자동 예약 발송한다. 공개 상세페이지에는 Solapi 명칭을 노출하지 않고, 관리자 기능 내부에서만 사용한다.

### Solapi 보안 조치
- Solapi API Key/Secret은 프론트엔드에 두지 않는다.
- 서버 환경변수 또는 Secret Manager에 저장한다.
- 문자 발송은 관리자 화면에서 직접 Solapi를 호출하지 않고 서버 API/Edge Function을 통해 실행한다.
- 발송 로그에는 전체 휴대폰 번호를 그대로 노출하지 않는다.
  - 예: `010-****-1234`
- 발송 실패 로그에도 개인정보 전문을 남기지 않는다.

### 문자 자동 예약 트리거
1. 예약 신청 완료 문자
   - 발송 시점: 사용자가 예약 신청을 제출한 즉시
   - 대상: 신청자 본인
   - 목적: 신청 접수 확인, 결제 확정 전이라는 점 안내
   - 예시 문구:
     - `[근력학교] 케틀벨 원데이 수업 예약 신청이 접수되었습니다. 결제 안내를 받으신 뒤 결제까지 완료되어야 자리가 확정됩니다.`

2. 결제 안내 문자
   - 발송 시점: 해당 일정의 결제 안내 대상자로 선정됐을 때
   - 대상: 예약 가능 인원 안에 들어온 신청자
   - 목적: 결제 링크 전달, 결제 마감 시간 안내
   - 예시 문구:
     - `[근력학교] 케틀벨 원데이 수업 결제 순서가 되었습니다. 아래 링크에서 결제를 완료해주세요. 결제 완료 시 자리가 확정됩니다. 결제 링크: {payment_url}`

3. 여석 안내 문자
   - 발송 시점: 취소/미결제로 자리가 생기고 다음 대기자가 선정됐을 때
   - 대상: 다음 대기자
   - 목적: 여석 발생 안내, 결제 유도
   - 예시 문구:
     - `[근력학교] 신청하신 케틀벨 원데이 수업에 여석이 생겼습니다. 아래 링크에서 결제하시면 자리가 확정됩니다. 결제 링크: {payment_url}`

4. 결제 완료 문자
   - 발송 시점: 결제 완료 확인 직후
   - 대상: 결제 완료자
   - 목적: 자리 확정, 수업 기본 정보 전달
   - 예시 문구:
     - `[근력학교] 케틀벨 원데이 수업 예약이 확정되었습니다. 일정: {class_date} / 장소: 근력학교 고대점 / 준비물: 편한 복장, 물`

5. 수업 전 리마인드 문자
   - 발송 시점: 수업 1일 전 오후 6시, 수업 당일 오전 9시
   - 대상: 결제 완료자
   - 목적: 노쇼 방지, 장소/준비물 재안내
   - 예시 문구:
     - `[근력학교] 내일 케틀벨 원데이 수업이 진행됩니다. 일정: {class_date} / 장소: 근력학교 고대점 / 준비물: 편한 복장, 물`

6. 수업 후 복습 자료 문자
   - 발송 시점: 수업 종료 1시간 후
   - 대상: 출석자 또는 결제 완료자
   - 목적: 복습 교재 링크 전달
   - 예시 문구:
     - `[근력학교] 오늘 수업 고생하셨습니다. 복습용 교재 링크를 보내드립니다. 링크: {notion_url}`

7. 복습 영상 안내 문자
   - 발송 시점: 영상 링크 준비 후 관리자가 승인했을 때
   - 대상: 출석자
   - 목적: 비공개 복습 영상 전달
   - 예시 문구:
     - `[근력학교] 케틀벨 원데이 수업 복습 영상 링크입니다. 집에서 다시 확인해보세요. 링크: {video_url}`

### 관리자 화면에 필요한 기능
- 문자 템플릿 관리
- 발송 대상 미리보기
- 발송 예약 시간 설정
- 자동 발송/수동 승인 선택
- 발송 성공/실패 로그
- 실패 문자 재발송
- 수신 거부/오입력 번호 제외

### 상태 연동
- 신청 완료 → 예약 신청 완료 문자
- 결제 안내 대상 선정 → 결제 안내 문자
- 결제 완료 → 결제 완료 문자 + 리마인드 예약 생성
- 수업 종료 → 복습 자료 문자 예약 생성
- 영상 링크 등록 → 복습 영상 안내 문자 발송 대기

## 추천 순서
- 지금은 1차 구현부터 진행
- 1차는 개인정보 저장 없이 일정 관리 편의만 개선
- 실제 예약 신청 데이터를 저장하는 순간 2차 서버/인증/보안 구조를 먼저 확정
- 서버 후보는 Supabase를 1순위로 검토
- GitHub Pages는 공개 상세페이지로만 유지
- 관리자 비밀번호 `8156`은 임시값으로 쓰되, 실제 서버 구현 시 프론트엔드/저장소에 노출하지 않음
