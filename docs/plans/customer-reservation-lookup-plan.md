# 수강생 본인 예약 조회 페이지 — 개발 계획 (초안)

**작성일:** 2026-06-13
**상태:** 계획 보고 (구현 전 — 백관장 검토 대기)

## 1. 목적

수강생이 **이름 + 전화번호**를 입력하면 본인이 신청한 예약의 **현재 상태**(신청 접수 / 대기 / 결제 안내 / 결제 완료 / 취소 등)를 직접 확인하는 페이지. "내 신청 어떻게 됐나요?" 문의를 줄이는 셀프 조회 창구.

## 2. 핵심 설계 결정 (검토 필요 항목)

### 2-1. 인증을 어떻게 할 것인가 — ⚠️ 가장 중요
이름+전화번호만으로 조회하면, **남의 번호를 알면 남의 신청도 볼 수 있다**(개인정보 노출). 세 가지 안:

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. 이름+전화 단순 일치** | 둘 다 정확히 맞으면 조회 | 구현 간단, 입력 편함 | 번호 아는 사람이 타인 조회 가능(약하지만 실제 위험은 낮음 — 이름까지 맞아야) |
| **B. 휴대폰 본인인증(SMS 인증번호)** | 전화번호로 인증번호 발송→입력 | 확실한 본인확인 | Solapi 인증번호 발송 비용·구현↑, UX 1단계 추가 |
| **C. 신청 시 발급한 조회 코드** | 접수 문자에 조회용 링크/코드 포함 | 안전+간편 | 접수 문자 구조 변경 필요, 코드 분실 시 곤란 |

→ **권장: A로 시작**(소규모·실명 기반이라 위험 낮음)하되, 노출 정보를 최소화(아래 2-3). 운영 중 민감하면 B로 승급. 백관장 의견 필요.

### 2-2. 조회 결과에 무엇을 보여줄 것인가
- ✅ 보여줄 것: 신청한 수업 일시·장소, 현재 상태(신청 접수/대기/결제 안내 중/결제 완료/취소), 다음 안내 예고.
- ❌ **숨길 것**: 개인 **대기 순번**(CLAUDE.md 정책 — 고객에게 순번 노출 금지), 다른 신청자 정보, 내부 메모.
- 상태 문구는 고객 언어로(예: payment_target → "결제 안내 대상 — 곧 결제 링크를 보내드립니다").

### 2-3. 개인정보 노출 최소화
- 일치하는 예약만, 본인 것만 반환. 전화번호는 마스킹해서 다시 표기(입력한 본인 확인용).
- 조회 실패 시 "일치하는 신청 내역이 없습니다"로 통일(존재 여부를 흘리지 않음).
- rate limiting(같은 IP/번호 단시간 다회 조회 차단)으로 무차별 조회 방지 — B안 아니면 권장.

## 3. 구현 구성 (A안 기준)

### 파일
- **신규** `lookup.html` (또는 index.html에 "내 예약 확인" 섹션 + 모달) — 이름·전화 입력 폼 + 결과 표시.
- **신규 Edge Function** `lookup-reservation` (공개, verify_jwt=false):
  - 입력: `{ applicant_name, phone }`
  - 처리: 검증(010 형식) → service_role로 `reservations` + `classes` 조회(이름·전화 정확 일치, 취소 포함 최근 건) → 고객용 상태 라벨로 변환 → 반환.
  - 출력: `{ ok, reservations: [{ class_label, place, status_label, applied_at }] }` (순번·내부필드 제외).
  - rate limiting: 간단히 같은 번호 N초 내 재요청 제한(메모리/테이블).
- **테스트**: 계약 테스트에 lookup.html 마크업·함수 필수 문자열 추가.

### 데이터/스키마
- 스키마 변경 **불필요**(기존 reservations·classes 조회만). B안 채택 시에만 인증코드 컬럼/테이블 추가.

### 보안
- service_role은 Edge Function에서만. 프론트는 anon 키로 함수 호출만.
- 이름+전화 둘 다 일치할 때만 반환. 부분 일치·번호 단독 조회 금지.

## 4. 작업 순서(예상)
1. 상태→고객 라벨 매핑 확정(백관장 문구 검토)
2. `lookup-reservation` 함수 작성 + 배포
3. `lookup.html`(또는 섹션) 작성, 함수 연동
4. 계약 테스트 추가, 배포
5. 본인 번호로 실조회 검증

## 5. 열린 질문 (백관장 결정 필요)
1. **인증 강도**: A(이름+전화) / B(SMS 인증번호) / C(조회 코드) 중 무엇으로?
2. 진입 동선: 별도 `lookup.html` 링크 / 기존 페이지 내 "내 예약 확인" 버튼?
3. 취소된 신청도 보여줄까, 활성 신청만?
4. 결과에 "다음 안내 예정" 같은 안내 문구를 넣을까?

> 위 결정만 주시면 구현은 기존 `submit-reservation` 패턴(공개 함수+service_role)을 그대로 재사용해 빠르게 가능합니다.
